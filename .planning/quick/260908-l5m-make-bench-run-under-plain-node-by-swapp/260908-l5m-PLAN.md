<decision>
## D-01 — Approach (b): extract a shared helper, not (a) import tests/ from bench/

Approach (a) — `bench/run.ts` importing `setup`/`teardown` from `tests/setup-native-abi.ts` — is
rejected for two reasons, one structural and one that is decisive here:

1. It inverts the dependency direction (a benchmark harness importing the test harness's private
   globalSetup), and couples bench to a file whose contract is "vitest calls me twice".
2. **It produces nothing committable.** `bench/` is entirely untracked WIP and `package.json` is
   already carrying the developer's unrelated in-flight changes. Under (a) the ENTIRE fix would live
   inside untracked WIP, so this task would either commit nothing at all or would have to sweep the
   developer's unfinished bench harness into its commit — explicitly forbidden by the brief.

Approach (b) yields `scripts/native-abi.mjs` — a genuinely reusable, self-contained module — plus a
thin-wrapper refactor of the tracked `tests/setup-native-abi.ts`. Both are committable on their own.
This is the repo's established **helper-first, call-site later** pattern (memory
`feedback_helper_first_callsite_later`): ship the shared helper as a self-contained commit and let the
consuming code absorb the swap when it lands.

**Language:** `.mjs`, not `.ts`. Every existing file in `scripts/` is `.mjs`
(`build-native-dual.mjs`, `postinstall.mjs`), Node runs it with no toolchain, and — critically — a
`.ts` helper would have to be executed through `tsx`, which is itself an uncommitted WIP devDependency.
A committed helper must not depend on uncommitted WIP. (`tests/` is in no tsconfig `include`, so the
TS→`.mjs` import introduces no typecheck surface; confirmed against `tsconfig.json` and
`tsconfig.node.json` on 2026-09-08.)

## D-02 — The swap must happen in a WRAPPER PROCESS, not inside bench/run.ts

The brief assumed a try/finally (plus signal handling) inside `bench/run.ts` would be sufficient.
**It is not.** Probed empirically on this machine (Windows 11, Node 22.23.0 / ABI 127) on 2026-09-08 —
swap the Node variant in, `require()` it, open and close a real `Database`, then attempt to restore:

| Restore strategy, in the process that loaded the binding | Result |
|---|---|
| `fs.copyFileSync(electronVariant, active)` | **EBUSY** |
| `fs.readFileSync` then `fs.writeFileSync` (buffer fallback) | **EBUSY** |
| `fs.renameSync(active, active + '.stale')` then copy | succeeded, but the `.stale` file could not be unlinked (**EPERM**) and had to be swept by a later process |

Once Windows has mapped `better_sqlite3.node` into a process, that process can never overwrite it.
So an in-process `finally` in `bench/run.ts` would fail to restore on **every single run** — silently
converting the "app stranded" failure mode from occasional into guaranteed. That is strictly worse
than the bug being fixed.

The fix: `scripts/with-node-abi.mjs` is a parent process that **never imports better-sqlite3**. It
activates the Node ABI, spawns the real command as a child, and restores after the child has exited.
The restore is then a plain `copyFileSync` into an unmapped file — verified working in the same probe
(the fresh-process repair step succeeded). As a bonus this removes the need to touch `bench/run.ts` at
all: only the three `package.json` script values change.

The rename-aside trick is deliberately NOT adopted: it leaves undeletable `.stale` droppings in
`build/Release/` and would change vitest teardown behavior, which D-03 forbids.

## D-03 — One shared library, two policies (`onLocked: 'warn' | 'throw'`)

vitest and bench want opposite things when the binary is locked by a running Electron app:

- **vitest** wants warn-and-continue, so that non-SQLite specs still run. This is load-bearing and
  must not regress.
- **bench** wants a hard failure — every bench path calls `buildCorpus()`, so continuing only buys a
  more confusing ABI stack trace downstream.

The library therefore takes an `onLocked` option defaulting to `'warn'`. `tests/setup-native-abi.ts`
passes nothing and keeps today's behavior byte-for-byte; the wrapper passes `'throw'`.

## Known limitation (documented, not fixed here)

A hard `taskkill /F` on the wrapper runs no handlers and will leave the Node variant active. That is
unrecoverable by design; the remedy is `pnpm rebuild:native:electron`, which the wrapper's failure
banner names. Ctrl-C — the realistic interrupt — IS handled.

Also observed but out of scope: today's vitest `teardown()` is subject to the same EBUSY reality
whenever a worker still holds the mapping, which is why memory `reference_vitest_abi_swap_breaks_app`
exists. Fixing vitest's restore would require the same wrapper-process treatment and is a separate
task. Do not widen this diff into it — note it in the summary.
</decision>
